# ch5 实验报告

## 总结实现的功能

主要包括以下几个方面：

1. **时间系统调用**：
   - 实现了 `sys_get_time` 系统调用，通过硬件计时器获取系统当前时间
   - 支持跨页面的 `TimeVal` 结构体，自动处理虚拟地址翻译

2. **动态内存映射系统调用**：
   - 实现了 `sys_mmap` 系统调用，支持进程动态映射内存区域
   - 实现了 `sys_munmap` 系统调用，支持进程取消映射内存区域
   - 添加了参数验证机制：地址对齐检查、长度验证、权限范围检查、重叠检查

3. **进程创建系统调用**：
   - 实现了 `sys_spawn` 系统调用，直接创建新进程执行指定程序
   - 与 fork+exec 不同，spawn 直接创建新的独立地址空间而不复制父进程内存

4. **内存管理优化**：
   - 在 `MemorySet` 中添加了 `check_overlap` 方法检查映射重叠
   - 在 `MemorySet` 中添加了 `remove_area_with_range` 方法移除完全匹配的映射区域
   - 修复了 `recycle_data_pages` 方法，确保进程退出时正确清理所有页表项和物理页框

5. **错误处理完善**：
   - sys_mmap：地址非对齐返回-1，长度为0返回-1，权限无效返回-1，与现有映射重叠返回-1
   - sys_munmap：地址非对齐返回-1，长度为0返回-1，没有完全匹配的映射区域返回-1
   - sys_spawn：程序不存在返回-1，创建失败返回-1

## sys_mmap 和 sys_munmap 的设计原理

### sys_mmap 的工作机制

**参数验证阶段**：
- 检查起始地址是否按页对齐（4KB对齐）
- 验证映射长度大于0
- 拒绝无效权限组合（prot=0或prot>7）
- 检查新映射区域与现有映射是否重叠

**映射建立阶段**：
- 将 POSIX 风格的权限标志转换为 RISC-V 页表权限位
- 计算虚拟地址范围对应的虚拟页号
- 创建 MapArea 对象（Framed 类型表示物理页动态分配）
- 内核自动为每一个虚拟页分配物理页框并建立页表项

### sys_munmap 的工作机制

**参数验证阶段**：
- 检查起始地址是否按页对齐
- 验证长度大于0
- 要求映射范围必须与现有 MapArea 完全匹配（既要起始地址相同，也要长度相同）

**映射移除阶段**：
- 查找与指定范围完全匹配的 MapArea
- 调用 unmap 清理该区域的所有页表项
- FrameTracker 析构时自动释放对应的物理页框
- 从内存集中删除该 MapArea

### 进程退出时的内存清理

当进程通过 `exit_current_and_run_next` 退出时：
- 调用 `recycle_data_pages()` 方法对所有 MapArea 进行清理
- 该方法先遍历所有 MapArea 调用 unmap 清理页表项
- 然后清空 areas 列表（FrameTracker 析构释放物理页）
- 这确保了进程占用的所有资源都被正确释放

## sys_spawn 的设计原理

### 基本概念

与 fork+exec 的对比：
- **fork+exec**：先复制父进程的完整地址空间（内存占用大），再加载新程序
- **spawn**：直接从 ELF 文件加载程序创建新地址空间（内存占用小，性能高）

### 创建流程

**步骤1 - 程序加载**：
- 从加载器获取指定程序的 ELF 数据
- 使用 `MemorySet::from_elf()` 解析 ELF 文件并建立内存映射

**步骤2 - 地址空间初始化**：
- 为新进程创建独立的 MemorySet（完全独立的虚拟地址空间）
- 包括用户栈、trap context、kernel stack 等必要区域

**步骤3 - 进程控制块创建**：
- 分配新的 PID（进程标识符）
- 分配新的 kernel stack
- 初始化 TaskControlBlock 的所有字段

**步骤4 - 父子关系建立**：
- 设置子进程的 parent 指针指向父进程
- 将子进程加入父进程的 children 列表
- 这允许父进程后续使用 waitpid 等待子进程

**步骤5 - 任务调度**：
- 将新创建的进程加入调度器的就绪队列
- 调度器在合适的时机为其分配 CPU 时间

### 返回值说明

- 成功：返回子进程的 PID
- 失败：返回 -1（程序不存在或其他错误）
- 子进程执行：被调度时自动从程序入口点开始执行


## Stride 调度算法深入

### 1. Stride 溢出问题分析

**问题场景**：
考虑两个进程 P1 和 P2，都有 pass = 10，使用 8 位无符号整数存储 stride：
- P1.stride = 255 (最大值)
- P2.stride = 250

当 P2 执行一个时间片后，其 stride 变为 250 + 10 = 260，在 8 位表示中溢出为 4 (260 & 0xFF = 4)。

**实际调度情况**：
下一次调度应该选择 stride 最小的进程。在 8 位无符号整数的循环表示中：
- 如果使用简单的数值比较：4 < 255，所以会选择 P2
- 但这违反了 stride 调度的初衷，因为 P2 刚才才运行过，应该轮到 P1

这说明在有溢出的情况下，简单的数值比较会导致错误的调度决策。

### 2. 为何要求优先级 >= 2

**解决溢出问题的条件**：

通过数学分析可以证明，在不考虑溢出的情况下，如果严格按照 stride 调度算法执行，且所有进程的优先级都 >= 2，则：

```
STRIDE_MAX - STRIDE_MIN <= BigStride / 2
```

**直观解释**：

1. **优先级最小为 2 的含义**：通过设置 `pass = BIG_STRIDE / priority`，当 priority 最小为 2 时，`pass` 最大为 `BIG_STRIDE / 2`。

2. **为什么这能解决溢出**：
   - 系统中最小的 stride 和最大的 stride 之差不会超过 `BIG_STRIDE / 2`
   - 如果我们选择 `BIG_STRIDE` 足够大（例如 2^16 = 65536），这个差值范围就足够大，不会在实际调度过程中频繁溢出
   - 更重要的是，即使发生溢出，两个 stride 之间的相对大小关系也能通过特殊的比较器正确判断

3. **传播性质**：
   - 初始时，所有进程的 stride = 0
   - 第一次选择时，选择任意进程（例如第一个），之后其 stride = pass
   - 由于所有进程的 pass 都来自 `BIG_STRIDE / priority`，且 priority >= 2
   - 所以运行中的进程之间的 stride 差值被限制在一个有限范围内

### 3. 处理溢出的特殊比较器

**核心思想**：

在有溢出的情况下，两个 stride 值的大小关系不能直接通过数值大小比较，而需要考虑它们在"逻辑时间轴"上的相对位置。

关键观察：
- 如果 `STRIDE_MAX - STRIDE_MIN <= BigStride / 2`，那么两个 stride 值的真实大小关系可以通过以下方式判断：
- 如果 `a - b` 在"短路径"上（即 `|a - b| <= BigStride / 2`），则直接比较
- 否则，说明一个经历了溢出，应该选择"另一个方向"更近的那个

**参考实现**：

使用 8 位表示，BigStride = 255 为例：
- `125 < 255` 为假，因为 125 表示的是"未来"的值（通过长路径）
- `129 < 255` 为真，因为 129 在短路径上确实小于 255

对于通用的 u64 类型和 `BIG_STRIDE = 1 << 16`：

```rust
use core::cmp::Ordering;

struct Stride(u64);

impl PartialOrd for Stride {
    fn partial_cmp(&self, other: &Self) -> Option<Ordering> {
        // 计算两个 stride 值的差，判断哪个更小
        // 使用有符号比较，避免溢出问题
        let diff = (self.0 as i64).wrapping_sub(other.0 as i64);
        let big_stride = (1u64 << 16) as i64;
        
        // 如果差值在 [-BigStride/2, BigStride/2) 范围内
        // 则 self.0 < other.0
        // 否则 self.0 > other.0
        if diff < big_stride / 2 && diff >= -(big_stride / 2) {
            // 直接比较
            Some(self.0.cmp(&other.0))
        } else if diff >= big_stride / 2 {
            // self 经历了溢出，实际上更小
            Some(Ordering::Less)
        } else {
            // other 经历了溢出，self 更大
            Some(Ordering::Greater)
        }
    }
}

impl PartialEq for Stride {
    fn eq(&self, other: &Self) -> bool {
        false
    }
}
```

**比较器的工作原理**：
- 计算两个 stride 的带符号差值
- 如果差值在 `[-BIG_STRIDE/2, BIG_STRIDE/2)` 范围内，说明不存在溢出干扰，直接比较数值
- 如果差值 >= `BIG_STRIDE/2`，说明 self - other 是一个大正数，这表示通过"长路径"相减，实际上 self < other（考虑了溢出）
- 如果差值 < `-BIG_STRIDE/2`，说明 self - other 是一个大负数，这表示 self > other
